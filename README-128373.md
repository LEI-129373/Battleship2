## 1. Identificação do Code Smell

O **Long Method**, descrito por Martin Fowler, ocorre quando um método contém demasiada lógica, dificultando a sua leitura, compreensão, manutenção e teste.

A principal técnica de refatorização utilizada foi **Extract Method**, que consiste em dividir um método extenso em métodos menores, com responsabilidades mais específicas, procurando manter o comportamento funcional do programa.

## 2. Mapeamento entre o Code Smell e o Qodana

| Propriedade | Valor |
|---|---|
| Code Smell de Fowler | Long Method |
| Inspeção IntelliJ/Qodana utilizada | Overly long method |
| ID da inspeção | `NonCommentSourceStatements` |
| Métrica utilizada | Número de instruções de código-fonte, excluindo comentários |
| Limite configurado | 30 instruções |
| Opção | `m_limit: 30` |
| Linter | `jetbrains/qodana-jvm-community:2026.2` |

A inspeção permite identificar métodos que ultrapassam o limite configurado de instruções.

O limite de 30 instruções foi definido para este trabalho. Não é apresentado como o valor por omissão da inspeção, que deve ser consultado na configuração original do IntelliJ/Inspectopedia.

### Limitações do mapeamento

A estratégia quantitativa descrita em *Object-Oriented Metrics in Practice* utiliza métricas como linhas de código e complexidade ciclomática, podendo combinar condições e limites relativos ao sistema.

A inspeção utilizada neste trabalho considera apenas o número de instruções, com um limite absoluto. Assim, não reproduz integralmente a estratégia do livro, nomeadamente a combinação de várias métricas através de condições lógicas.

```yaml

name: Qodana Long Method 129373

on:
  pull_request:
  push:
  workflow_dispatch:

permissions:
  contents: read
  checks: write
  pull-requests: write

jobs:
  qodana:
    name: Qodana Long Method 129373
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha || github.sha }}
          fetch-depth: 0

      - name: Run Qodana
        uses: JetBrains/qodana-action@v2026.2
        with:
          args: --config qodana-129373.yaml
          pr-mode: false
          use-annotations: true
          post-pr-comment: true
          upload-result: true
```

O workflow executa a análise em eventos `push`, `pull_request` e através de execução manual (`workflow_dispatch`).

A opção `pr-mode: false` permite executar a análise fora do modo limitado às alterações do Pull Request.

## 4. Quality Gate

O objetivo do quality gate é detetar automaticamente problemas relacionados com o Code Smell Long Method.

Para a inspeção escolhida, pretende-se obter **zero métodos que ultrapassem o limite configurado de 30 instruções**.

Quando a análise não satisfaz as condições de falha configuradas, o job do GitHub Actions termina com erro. Quando as condições são satisfeitas, o job pode terminar com sucesso.

## 5. Métodos identificados e refatorizações

Durante a análise inicial foram identificados quatro métodos excessivamente longos:

| Ficheiro | Método | Instruções iniciais |
|---|---|---:|
| `src/main/java/battleship/Move.java` | `processEnemyFire()` | 77 |
| `src/main/java/battleship/Tasks.java` | `menu()` | 77 |
| `src/main/java/restserver/AiShotStrategy.java` | `computeShots()` | 31 |
| `src/main/java/restserver/CallbackClient.java` | `sendShots()` | 32 |

### Refatorizações realizadas

**Move.java:** foi separada a lógica de processamento dos tiros, apresentação de resultados e construção da resposta JSON.

**Tasks.java:** foi extraída a lógica de execução dos comandos do menu, mantendo o estado da frota e da partida através de uma estrutura auxiliar.

**AiShotStrategy.java:** foi extraída parte da lógica de seleção dos disparos para um método auxiliar.

**CallbackClient.java:** foram separadas responsabilidades relacionadas com a preparação do pedido HTTP, o tratamento da resposta e o resultado da jogada.

Estas alterações tiveram como objetivo reduzir a dimensão dos métodos e melhorar a separação de responsabilidades.

## 8. Reflexão sobre os resultados

O Qodana permitiu identificar métodos excessivamente longos no projeto Battleship2 e acompanhar o efeito das refatorizações através do GitHub Actions. A inspeção pode originar falsos positivos, quando um método longo continua a ser claro e adequado, ou falsos negativos, quando um método com poucas instruções apresenta lógica complexa. O resultado é sensível ao limite configurado: um valor mais baixo aumenta o número de deteções, enquanto um valor mais alto reduz esse número. Em comparação com as estratégias quantitativas apresentadas em *Object-Oriented Metrics in Practice*, esta configuração é uma aproximação, pois não combina várias métricas nem utiliza limites relativos à distribuição das métricas do sistema.
