## 1. Identificação do Code Smell

O **Long Method**, descrito por Martin Fowler, ocorre quando um método contém demasiadas instruções, acumulando lógica que dificulta a leitura, compreensão, manutenção e teste do código.

A refatorização utilizada para corrigir este problema foi principalmente **Extract Method**, que consiste em extrair partes da lógica para métodos mais pequenos e com responsabilidades específicas, procurando preservar o comportamento original.

## 2. Correspondência com a inspeção do Qodana

| Propriedade | Valor |
|---|---|
| Code Smell | Long Method |
| Inspeção IntelliJ/Qodana | Overly long method |
| ID da inspeção | `NonCommentSourceStatements` |
| Métrica | Número de instruções de código-fonte, excluindo comentários |
| Limite configurado | 30 instruções |
| Opção de configuração | `m_limit: 30` |
| Severidade observada | High |
| Linter | `jetbrains/qodana-jvm-community:2026.2` |

A inspeção `NonCommentSourceStatements` identifica métodos cujo número de instruções ultrapassa o limite configurado.

Neste trabalho foi utilizado o valor de **30 instruções**, definido explicitamente no perfil de inspeções. Este valor corresponde ao limite adotado para o trabalho, não sendo apresentado como um valor predefinido universal da ferramenta.

### Limitações da inspeção

- Mede o número de instruções, não o número de linhas de código.
- Não avalia diretamente a complexidade cognitiva ou ciclomática.
- Um método com menos de 30 instruções pode continuar a ser difícil de compreender.
- Um método com mais de 30 instruções não é necessariamente incorreto.
- A extração de métodos deve melhorar a organização e a legibilidade, não apenas reduzir a contagem de instruções.

Assim, esta inspeção funciona como um indicador automático de possíveis problemas de manutenção, mas não substitui a avaliação humana da qualidade do código.

## 4. Integração contínua com GitHub Actions

O Qodana foi integrado no GitHub Actions através do workflow:

`.github/workflows/qodana-smell-129373.yaml`

```yaml
# 129373
name: Qodana Long Method 129373

on:
  pull_request:
  push:
  workflow_dispatch:

permissions:
  contents: read
  checks: write
  pull-requests: write

jobs:
  qodana:
    name: Qodana Long Method 129373
    runs-on: ubuntu-latest

    steps:
      - name: Checkout repository
        uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha || github.sha }}
          fetch-depth: 0

      - name: Run Qodana
        uses: JetBrains/qodana-action@v2026.2
        with:
          args: --config qodana-129373.yaml
          pr-mode: false
          use-annotations: true
          post-pr-comment: true
          upload-result: true
```

O workflow é executado automaticamente em eventos `push` e `pull_request`, podendo também ser iniciado manualmente através de `workflow_dispatch`.

A opção `pr-mode: false` configura a execução fora do modo de análise limitada às alterações do Pull Request.

A opção `upload-result: true` permite guardar os resultados da análise como artefactos do GitHub Actions.

## 6. Identificação e correção dos problemas

Durante o desenvolvimento, foram identificados quatro métodos com dimensão superior ao limite definido.

| Ficheiro | Método | Instruções identificadas |
|---|---|---:|
| `src/main/java/battleship/Move.java` | `processEnemyFire()` | 77 |
| `src/main/java/battleship/Tasks.java` | `menu()` | 77 |
| `src/main/java/restserver/AiShotStrategy.java` | `computeShots()` | 31 |
| `src/main/java/restserver/CallbackClient.java` | `sendShots()` | 32 |

### 6.1. Refatorização de `Move.java`

O método `processEnemyFire()` concentrava o processamento dos resultados dos tiros, a apresentação de mensagens e a construção da resposta JSON.

A lógica foi distribuída por métodos auxiliares, separando o cálculo dos resultados, a apresentação das informações e a construção da resposta.

### 6.2. Refatorização de `Tasks.java`

O método `menu()` concentrava a leitura dos comandos e o tratamento das diferentes operações do jogo.

Foi aplicado **Extract Method** para separar a execução dos comandos do ciclo principal do menu.

Foi também introduzida uma estrutura auxiliar para manter o estado da frota e da partida entre comandos.

### 6.3. Refatorização de `AiShotStrategy.java`

O método `computeShots()` continha várias etapas de seleção de posições para os disparos da inteligência artificial.

Parte dessa lógica foi extraída para um método auxiliar, reduzindo o número de instruções do método principal.

### 6.4. Refatorização de `CallbackClient.java`

O método `sendShots()` reunia a preparação do pedido HTTP, o envio, a validação da resposta e o tratamento do resultado da jogada.

Estas responsabilidades foram distribuídas por métodos auxiliares, tornando o fluxo principal mais curto e organizado.
