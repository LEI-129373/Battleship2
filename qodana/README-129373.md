## 1. Identificação do Code Smell

O **Long Method**, descrito por Martin Fowler, ocorre quando um método contém demasiadas instruções, dificultando a leitura, compreensão, manutenção e teste do código.

A principal técnica de refatorização utilizada foi **Extract Method**, que consiste em dividir um método extenso em métodos mais pequenos, com responsabilidades específicas, procurando preservar o comportamento original do programa.

## 2. Mapeamento entre o Code Smell e o Qodana

| Propriedade | Valor |
|---|---|
| Code Smell | Long Method |
| Inspeção IntelliJ/Qodana | Overly long method |
| ID da inspeção | `NonCommentSourceStatements` |
| Métrica | Número de instruções de código-fonte, excluindo comentários |
| Limite configurado | 30 instruções |
| Opção | `m_limit: 30` |
| Linter | `jetbrains/qodana-jvm-community:2026.2` |

A inspeção `NonCommentSourceStatements` identifica métodos que ultrapassam o limite de instruções configurado.

O valor de 30 instruções foi definido especificamente para este trabalho, não sendo assumido como o valor por omissão da ferramenta.

### Limitações da inspeção

A inspeção utiliza um limite absoluto de instruções, não avaliando diretamente a complexidade ciclomática ou a complexidade cognitiva do método.

A estratégia quantitativa apresentada em *Object-Oriented Metrics in Practice* pode combinar várias métricas e utilizar limites relativos ao sistema. Por isso, a inspeção utilizada representa uma aproximação à deteção do Long Method, não reproduzindo integralmente a estratégia do livro.

## 4. Quality Gate

O objetivo do quality gate é detetar automaticamente problemas relacionados com o Code Smell Long Method.

Para a inspeção escolhida, pretende-se obter **zero métodos que ultrapassem o limite configurado de 30 instruções**.

Quando a análise não satisfaz as condições configuradas, o GitHub Actions apresenta uma falha. Quando as condições são satisfeitas, o workflow pode terminar com sucesso.

## 5. Identificação e refatorização dos problemas

A análise inicial identificou quatro métodos excessivamente longos:

| Ficheiro | Método | Instruções iniciais |
|---|---|---:|
| `../src/main/java/battleship/Move.java` | `processEnemyFire()` | 77 |
| `../src/main/java/battleship/Tasks.java` | `menu()` | 77 |
| `../src/main/java/restserver/AiShotStrategy.java` | `computeShots()` | 31 |
| `../src/main/java/restserver/CallbackClient.java` | `sendShots()` | 32 |

### Refatorizações realizadas

**Move.java:** foi separada a lógica de processamento dos tiros, apresentação dos resultados e construção da resposta JSON.

**Tasks.java:** foi extraída a lógica de execução dos comandos do menu, mantendo o estado da frota e da partida através de uma estrutura auxiliar.

**AiShotStrategy.java:** foi extraída parte da lógica de seleção dos disparos para um método auxiliar.

**CallbackClient.java:** foram separadas responsabilidades relacionadas com a preparação do pedido HTTP, o tratamento da resposta e o resultado da jogada.

Estas alterações tiveram como objetivo reduzir a dimensão dos métodos e melhorar a organização do código.

## 8. Reflexão sobre os resultados

O Qodana permitiu identificar métodos excessivamente longos no projeto Battleship2 e acompanhar o efeito das refatorizações através do GitHub Actions. A inspeção pode produzir falsos positivos, quando um método longo continua a ser claro e adequado, ou falsos negativos, quando um método com poucas instruções apresenta lógica complexa. O resultado é sensível ao limite configurado: um valor mais baixo aumenta o número de deteções, enquanto um valor mais alto reduz esse número. Em comparação com as estratégias apresentadas em *Object-Oriented Metrics in Practice*, esta configuração é uma aproximação, pois não combina várias métricas nem utiliza limites relativos à distribuição das métricas do sistema.
