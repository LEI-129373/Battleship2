## 1. Identificação do Code Smell

A **Empty Class** (variante direta da **Lazy Class**), descrita por Martin Fowler, ocorre quando uma classe não possui responsabilidades suficientes para justificar a sua existência no sistema (ou quando é completamente vazia, sem métodos ou atributos úteis). Este tipo de classe adiciona complexidade desnecessária à estrutura do projeto, aumentando o esforço de manutenção e navegação sem trazer qualquer valor ao software.

A principal técnica de refatorização utilizada para eliminar este *code smell* é a **Inline Class** (ou remoção de ficheiro redundante via *Safe Delete*), que consiste em eliminar a classe sem conteúdo ou incorporar eventuais comportamentos remanescentes noutra classe existente, mantendo a integridade funcional do sistema.

---

## 2. Mapeamento entre o Code Smell e o Qodana

| Cheiro (Fowler) | Inspeção no IDE | ID da inspeção | Métrica / limiar | Limitações |
|---|---|---|---|---|
| Lazy Class / Empty Class | Class is empty | `EmptyClass` | $NOM = 0$ e $NOA = 0$ (Classe sem métodos nem atributos) | O livro exige $NOM \le 4$ e $NOA \le 2$ (limiares de métricas reduzidas); o Qodana apenas deteta classes 100% vazias via análise estrutural (AST), não permitindo verificar classes pequenas com métodos triviais nem usar limiares relativos. |

| Propriedade | Valor |
|---|---|
| Code Smell | Empty Class / Lazy Class |
| Inspeção IntelliJ/Qodana | Class is empty |
| ID da inspeção | `EmptyClass` |
| Métrica | Presença de declarações (métodos ou atributos) no corpo da classe |
| Limite configurado | 0 elementos (Classe sem conteúdo) |
| Opção | `enabled: true` |
| Linter | `jetbrains/qodana-jvm-community:2026.2` |

O Qodana assinala classes Java onde não existam métodos ou atributos úteis declarados. A estratégia descrita no livro *Object-Oriented Metrics in Practice* aborda a *Lazy Class* de forma quantitativa através de limiares reduzidos de $NOM$ (Number of Methods) e $NOA$ (Number of Attributes).

### Limitações da inspeção

A estratégia de deteção descrita no livro avalia a escassez de responsabilidades combinando limiares reduzidos de métricas ($NOM \le 4$ e $NOA \le 2$).

A inspeção `EmptyClass` do Qodana for JVM efetua uma análise estática estrita (AST), detetando apenas classes totalmente vazias. Não deteta classes que contêm 1 ou 2 métodos getters/setters triviais que continuam a ser *Lazy Classes*. Além disso, a regra é binária (presença/ausência de código), não dependendo de um valor numérico configurável de métrica.

## 4. Quality Gate

O objetivo do *quality gate* é impedir que cheguem ao ramo principal classes sem qualquer conteúdo ou utilidade.

Para a inspeção configurada, exige-se **zero ocorrências de classes vazias**.

Quando a análise descobre uma classe vazia no repositório, o GitHub Actions marca o *job* como **Failure**. Quando não é detetada nenhuma violação, o workflow termina com **Success**.

## 8. Reflexão sobre os resultados

A inspeção `EmptyClass` do Qodana detetou com exatidão a classe vazia `Test.java`, constituindo um verdadeiro positivo. Contudo, em termos gerais de qualidade de código, esta inspeção apresenta um risco elevado de falsos negativos: uma *Lazy Class* que possua apenas um atributo desnecessário ou um método getter simples não é capturada por esta regra, apesar de continuar a constituir um *code smell* segundo Martin Fowler. A regra é puramente determinística e estrutural, dependendo da presença ou ausência de elementos no código. Em comparação com as estratégias do livro *Object-Oriented Metrics in Practice*, a solução no Qodana representa uma aproximação focada na vertente estrutural, já que o linter não disponibiliza métricas combinadas de $NOM$ e $NOA$ com regras lógicas compostas.
